## 0. 最高执行指令

你现在负责开发 **“智能多式联运物流数据系统”**。这是一个需要真实运行、持续开发、后续可部署和扩展的正式业务系统，不是静态 Demo、纯 UI 原型、一次性展示页或仅用于截图的前端项目。

开发前必须完整阅读项目中提供的全部需求规格，理解角色、业务对象、状态、数据权限和前后模块衔接。**不要机械按照需求文档章节顺序堆页面**，但不得擅自改变需求中已经明确的业务规则。

系统最终必须满足：

- 真实登录、真实用户、真实角色、真实权限；
- 真实后端 API、真实数据库、真实数据持久化；
- 真实 CRUD、真实状态流转、真实业务闭环；
- 真实企业级数据权限，不允许仅前端隐藏；
- 真实地图底图、真实地理节点、真实路径数据来源；
- 业务轨迹、GPS/AIS、铁路节点等来自后端或正式数据接入接口；
- 真实日志审计和操作留痕；
- AI 智能体必须继承用户权限，只做辅助，不代替业务人员完成关键确认；
- 每个开发阶段必须启动真实系统、打开浏览器，并使用 `playwright-skill` 验收。

### 0.1 严禁事项

严禁以下实现：

- 前端 Mock JSON 代替数据库；
- 把运输需求、路线、车辆、企业、订单、轨迹直接写死在 Vue 组件；
- 使用 localStorage 作为业务数据库；
- 新增/修改/删除仅操作前端数组；
- 页面按钮只有 UI 没有 API 和业务逻辑；
- 刷新页面或重启后端后数据丢失；
- 所有角色登录后看到相同菜单或相同企业数据；
- 仅通过前端菜单隐藏实现权限；
- 由 Vue 直接决定“已成交、已生效、已完成、已结算”等核心状态；
- 地图上手工画两点直线冒充实际道路/铁路/航运路线；
- 用随机坐标、随机轨迹冒充真实运行数据；
- 把高德 Key、JWT Secret、数据库密码等写入仓库；
- 建大量空壳页面冒充系统完成度；
- 为了减少菜单，把多个独立业务强行塞进一个页面十几个 Tab；
- 把开发测试数据包装成“真实生产数据”。

如果暂时无法获得生产业务数据，开发环境允许使用**数据库持久化的测试样本数据**，但必须显式标记 `isTestData=true` / “开发样例”，且生产验收必须替换为真实接口数据或用户提供的脱敏真实业务数据。

任何 Skill 都不得推翻需求规格已经明确的角色职责、数据权限、状态和业务边界。

# 2. 需求来源与已确认业务范围

PC 端主要角色：

1. **粮食贸易企业**：运输需求发起方、方案选择方、供需匹配确认方、合同委托方、运输过程查看方、对账确认方。
2. **物流运营商**：运输供给发布方、报价/议价方、承运方、联运组织和执行编排方、账单发起方。
3. **平台运营方**：平台运营、规则与基础数据维护、全量业务查看、数据治理、异常核查、系统管理和数据产品管理。

移动端角色：

4. **司机**：仅通过司机微信小程序接收本人任务，反馈装货、发运、在途、到达、卸货、签收、异常、单据，不进入 PC 业务后台。

### 2.1 核心端到端主链路

```text
交易订单
  ↓
运输需求
  ├─→ 直接发布供需匹配
  └─→ 多式联运方案求解 → 选择完整方案 → 发布供需匹配
            ↓
供需匹配大厅（公开竞价 / 指定议价 / 从供给反向对接）
            ↓
确认承运与最终成交价格
            ↓
合同签署并生效
            ↓
联运组织（一次委托 / 一单制或传统联运）
            ↓
如需散改集：粮食批次 → 车辆 → 集装箱 → 船舶/航次
            ↓
运输任务 / 分段任务 / 执行任务
            ↓
司机小程序执行 + 外部 GPS/AIS/铁路节点数据
            ↓
EPCIS 标准事件链
            ↓
联运跟踪 / 运输全程可视化 / ETA / 风险预警
            ↓
任务完成
            ↓
账单 → 对账 → 结算留痕
```

# 3. 技术架构

采用前后端分离 + Monorepo。

## 3.1 PC Web

- Vue 3
- TypeScript
- Vite
- Vue Router
- Pinia
- Element Plus
- ECharts
- Axios
- GSAP（仅用于必要的微动效、地图联动、状态切换，不做炫技动画）

## 3.2 地图

- AMap JSAPI 2.0
- 高级可视化优先使用高德官方 WebGL / Loca 能力
- 轨迹、线路、Marker、Polygon、InfoWindow、缩放聚合均封装成独立地图模块
- 高德相关凭据只能放环境变量

建议环境变量：

```env
VITE_AMAP_KEY=
VITE_AMAP_SECURITY_JS_CODE=
```

必须提供 `.env.example`，不得提交真实 Key。

## 3.3 后端

- Node.js
- NestJS
- TypeScript
- RESTful API
- Swagger / OpenAPI
- WebSocket 或 SSE：用于在途位置、事件、风险等增量推送；必须保留 HTTP 查询兜底

## 3.4 数据库

第一阶段使用 **SQLite + Prisma ORM**：

- Prisma Schema
- Prisma Migration
- Prisma Seed
- Prisma Client

SQLite 是正式开发阶段数据库，不是 Mock 数据库。Service 层不得大量依赖 SQLite 特有语法，必须为后续迁移 PostgreSQL / MySQL 留出空间。

动态高频轨迹采用独立 `TrackPoint` / `LocationSnapshot` 表，不允许把数万轨迹点塞入一个 JSON 字段。

## 3.5 推荐目录

```text
/apps
  /web                 # PC Web
  /api                 # NestJS API
  /driver-mini         # 司机端微信小程序（建议 uni-app + Vue3 + TS）
/packages
  /shared              # 共享类型、枚举、校验模型
  /ui                   # 公共 UI 组件
  /map                  # 高德地图封装
  /business-rules       # 可复用业务规则与状态定义
/prisma
  schema.prisma
  migrations/
  seed/
/docs
  architecture/
  api/
  database/
  acceptance/
/tools
  /data-import          # 真实基础数据导入
  /data-validation      # 数据真实性与坐标校验
  /dev-simulator        # 仅开发测试可用，与正式接入接口隔离
/public
  /assets/grain         # 粮食示意图
```

# 5. PC 页面布局：顶部导航 + 红白配色

## 5.1 强制布局

PC 后台**不使用左侧全局导航栏**。整体结构固定为：

```text
┌────────────────────────────────────────────────────────────────┐
│ Logo + 系统名称 | 顶部一级导航 ... | 更多 | 用户/主体 | 退出 │
├────────────────────────────────────────────────────────────────┤
│ Breadcrumb / 当前业务位置                                      │
├────────────────────────────────────────────────────────────────┤
│ 页面内容：筛选区 → 工具栏 → 主体内容 → 分页/详情                │
└────────────────────────────────────────────────────────────────┘
                                               ● AI悬浮小人
```

参考本次提供的页面截图，但不要逐像素照抄，应沿用其简洁、企业后台、顶部导航、红色激活态的方向。

## 5.2 视觉 Token

主视觉采用**红 + 白 + 浅灰**：

```css
--brand-primary: #E52B2F;
--brand-primary-hover: #D52227;
--brand-primary-soft: #FFF2F2;
--text-primary: #1F2329;
--text-secondary: #646A73;
--text-placeholder: #A0A5AD;
--page-bg: #F5F6F8;
--surface: #FFFFFF;
--border: #E7E9EE;
--divider: #EEF0F3;
--success: #18A058;
--warning: #F59E0B;
--danger: #E03131;
--info: #2F80ED;
```

原则：

- 顶部栏白底；
- 当前一级导航使用红色文字/红色下划线；
- 主操作按钮红色；
- 次要操作白底灰边；
- 页面背景浅灰；
- 内容卡片白底，尽量少阴影；
- 不使用大面积红色背景；
- 不使用全局暗黑、霓虹、玻璃拟态；
- 运输全程可视化也保持浅色商务地图风格，仅地图业务图层使用多运输方式编码色。

- Header：64~68px；
- 一级导航高度与 Header 一致；
- Breadcrumb：40~44px；
- 页面外边距：24px（≥1440px 屏幕可 28~32px）；
- 内容卡圆角：6~8px；
- 表格行高：48~52px；
- 页面建议适配宽度：1280~1920；
- 禁止 Header 横向滚动。

# 6. 顶部导航与“更多”规则

## 6.1 一级导航建议顺序

```text
首页
供需管理
联运方案
供需匹配
合同管理
联运服务
全程可视化
对账结算
数据服务（数据要素产品）
系统管理
```

其中：

- “AI智能体中心”**不占用顶部一级导航**，统一改为页面右下角悬浮小人入口；
- “数据服务”是用户界面展示名，内部业务对象仍使用“数据要素产品”；
- “系统管理”仅平台运营方显示；
- 不同角色先做权限过滤，再做导航宽度计算。

## 6.2 顶部导航放不下时

必须实现真正的动态 Overflow，而不是写死某几个菜单永远在“更多”。

实现要求：

1. 使用 `ResizeObserver` 监听 Header 宽度；
2. 固定保留：Logo、系统名称、首页、用户区、更多；
3. 根据 `displayOrder + overflowPriority` 从右向左将低优先级菜单移动到“更多”；
4. 当前路由即使位于“更多”内部，“更多”也显示激活态；
5. 窗口变宽后菜单自动恢复到顶部；
6. “更多”为空时不显示；
7. 不允许导航文字压缩到难以阅读，不允许水平滚动。

建议默认优先收纳：

```text
系统管理 → 数据服务 → 对账结算 → 全程可视化
```

但最终必须按实际宽度动态处理。

有二级菜单的一级导航采用下拉菜单：


# 7. 菜单与 Tab 强制规则

菜单用于独立业务功能导航；Tab 只用于同一业务对象/同一业务功能的局部视图。

具备下列任一特征，应优先建设独立页面/路由：

- 独立业务目标；
- 独立列表；
- 独立筛选；
- 独立 CRUD；
- 独立权限；
- 独立流程；
- 独立数据对象。

允许的 Tab 示例：

- 供需匹配大厅：需求大厅 / 供给大厅；
- 联运组织管理：全部 / 一单制 / 传统联运（作为列表过滤视图）；
- 运输专题视图：公路 / 铁路 / 水运；
- 日志管理：登录日志 / 操作日志 / 数据变更 / 接口日志；
- 详情对象内部：基本信息 / 关联对象 / 操作记录。

# 8. 页面统一设计规范

## 8.1 列表页

标准结构：

1. Breadcrumb；
2. 页面标题 + 简短说明（说明可省略）；
3. 独立筛选区；
4. 列表工具栏；
5. 表格/卡片主体；
6. 分页；
7. 详情抽屉或独立详情路由。

**新增按钮不要与搜索字段挤在同一行。**

- 筛选区只放查询条件 + 搜索/重置；
- “新建运输需求 / 新建供给 / 新建账单”等放在列表工具栏右上方；
- 通用 CRUD 操作如“查看详情、编辑、删除”优先收纳到“更多”菜单；
- 关键业务动作如“发布匹配、开始求解、报价、确认承运、下发任务、提交对账”可作为清晰的主业务按钮。

## 8.2 详情页

详情页需要回答：

- 这是什么业务对象；
- 来源是什么；
- 当前状态是什么；
- 下一步能做什么；
- 关联了哪些上下游对象；
- 历史发生了什么。

关键业务对象必须有“业务链穿透”能力，例如：

```text
交易订单 → 运输需求 → 方案 → 匹配 → 合同 → 联运业务 → 任务 → 账单
```

## 8.3 状态显示

状态来自后端，不允许前端自行判断核心状态。

颜色只作为辅助：

- 草稿/未开始：灰；
- 进行中：蓝；
- 待处理：橙；
- 成功/完成：绿；
- 异常/失败：红。

# 10. 供需管理

## 10.1 运输需求管理

正式上游只允许来自 **交易订单**。

必须支持：

- 从交易订单选择明细生成运输需求；
- 自动带入货主、收货方、粮食品种、规格、订单数量等；
- 校验“本次运输数量 ≤ 剩余可运输数量”；
- 起运省市区、起运节点/地址；
- 目的省市区、目的节点/地址；
- 计划发运时间、要求到达时间；
- 意向运输方式；
- 是否允许多式联运；
- 是否允许中转；
- 公开竞价 / 指定议价发布设置；
- 直接发布至匹配大厅；
- 进入多式联运方案求解；
- 撤回发布；
- 取消需求；
- 查看匹配和议价记录。

粮食贸易企业可维护本企业需求；物流运营商不可创建需求；平台运营方可查看全量并进行治理。

- 适用粮食品种；
- 可服务时间；
- 参考运输时长；
- 参考价格/计价单位；
- 特色服务能力；
- 有效期；
- 草稿/已发布/暂停/已失效状态。

只有“已发布且有效”的供给进入供给大厅。

# 18. 地图、路径与“真实数据”规范

这是本项目最重要的实现原则之一。

## 18.1 底图

必须使用高德真实在线底图，不得用静态中国地图图片代替业务地图。

地图必须实现：

- 缩放；
- 拖拽；
- 图层开关；
- Marker 聚合；
- 节点点击；
- 列表与地图双向联动；
- 轨迹 Polyline；
- 轨迹回放；
- 计划/实际线路区分；
- 风险点；
- 任务筛选；
- 适配大量点位的性能策略。

## 18.2 公路路径

公路路径必须通过高德正式路线规划能力或已接入的真实路径服务计算并返回：

- 路线 Geometry；
- 实际里程；
- 预计时长；
- 路段信息（可用时）；
- 查询时间；
- 路径服务来源。

禁止使用起终点直线代替道路路径。

如果账号权限不具备货车专用路径服务，必须：

- 使用当前有权限的正式道路路线能力；
- 在数据中记录 `routeProfile`；
- UI 明确这是“通用道路参考路线”而非货车限行级路径；
- 后续获得货车路线能力后无缝替换。

## 18.3 铁路路径

高德道路路线规划不能冒充铁路货运路径。

铁路路径必须来自：

- 已维护且经过核验的真实铁路站点；
- 真实铁路线路主数据；
- 铁路业务系统/行业接口；
- 或人工导入的可追溯真实线路几何。

地图展示必须按实际铁路走向，不得简单两点连线；数据不足时宁可只展示“节点进度 + 已核验线路”，也不能生成虚构铁路。

## 18.4 水运路径

水运位置和航迹优先来自 AIS 数据。

必须区分：

- 实时 AIS；
- 历史 AIS；
- 航次计划；
- 计划航线。

如果没有实时 AIS，就显示“历史轨迹/计划航线”，不能标成“实时”。

## 18.5 基础地理主数据

港口、铁路站、粮库、物流园区、仓库等必须有：

- 标准名称；
- 类型；
- 省市区；
- 经度纬度；
- 数据来源；
- 更新时间；
- 数据质量状态。

坐标必须经过高德坐标系处理和抽查。

## 18.6 轨迹数据

轨迹不得在前端写死。

公路：

```text
车辆终端/GPS → ingest API → TrackPoint → 最新位置 → 地图/ETA
```

水运：

```text
AIS Provider → ingest API → VesselTrackPoint → 最新位置 → 地图/ETA
```

铁路：

```text
铁路节点/状态接口 → RailTransportEvent → 节点进度 → 地图/时间轴
```

## 18.7 数据真实性分级

所有数据增加来源标识：

```text
sourceType: INTERNAL | AMAP | GPS | AIS | RAIL | MOBILE | MANUAL_VERIFIED | TEST
sourceSystem
sourceRecordId
sourceTimestamp
ingestedAt
dataQuality
isTestData
```

规则：

- 生产业务页面默认不显示 `TEST` 数据；
- 开发阶段样本必须数据库持久化，但要明确“测试样本”；
- 不得把随机坐标/模拟订单描述为真实生产数据；
- 验收环境优先导入用户提供的脱敏真实业务数据。

# 26. 数据权限

数据权限必须在 API / Service 层自动注入。

## 26.1 粮食贸易企业

- 可维护本企业运输需求；
- 可查看全部公开运输供给；
- 可查看本企业发起/参与的匹配、合同、运输和账单；
- 可查看平台公开信息；
- 不可查看其他贸易企业私有需求、合同、任务、结算。

## 26.2 物流运营商

- 可维护本企业运输供给；
- 可查看公开需求/方案；
- 可查看指定给本企业的定向业务；
- 不可查看指定给其他物流运营商的定向业务；
- 可查看本企业承运业务、任务、司机、账单；
- 不可查看其他物流运营商私有报价。

## 26.3 平台运营方

可按权限查看全平台数据，但对于“确认承运、合同双方确认、对账确认”等商业动作不得代替业务主体执行。

## 26.4 司机

只允许查看和操作本人被分配的执行任务。

任何 API 必须校验：

- 当前用户；
- 所属主体；
- 角色；
- 权限；
- businessEntityId；
- 业务参与关系。

不得只靠前端传入 `enterpriseId` 决定数据范围。

# 28. 核心状态机

## 28.1 运输需求

```text
草稿
→ 已发布
→ 匹配中
→ 议价中
→ 待确认
→ 部分匹配 / 匹配完成
→ 已取消

匹配失败：匹配中/议价中 → 待重新匹配
```

## 28.2 匹配发布

```text
待报价
→ 竞价中 / 议价中
→ 待确认
→ 已成交
→ 已关闭
```

## 28.3 合同

```text
草稿 → 待确认 → 已签署 → 已生效 → 已终止
```

## 28.4 联运业务

```text
待组织
→ 已组织
→ 待执行
→ 执行中
→ 中转中（可返回执行中）
→ 已完成

任意执行阶段可进入异常标识；
业务取消/合同终止 → 已终止
```

## 28.5 司机执行任务

```text
待确认
→ 待装货
→ 已装货
→ 运输中
→ 已到达
→ 待签收
→ 已完成

可伴随异常状态，不应靠前端任意改值。
```

## 28.6 账单

```text
草稿
→ 待对账
→ 对账中
→ 差异处理中
→ 已确认
→ 已作废
```

状态流转只能由 NestJS Service 中的业务方法执行，必须校验当前状态与操作权限。

# 41. 最终验收原则

本系统的验收标准不是“页面看起来像一个系统”，而是：

- 业务操作通过真实 API 写入数据库；
- 刷新和重启服务后数据仍存在；
- 不同角色有真实权限差异；
- 不同企业有真实数据范围差异；
- 顶部菜单来自权限配置；
- 菜单放不下会自动进入“更多”；
- 核心业务状态由后端控制；
- 需求→方案→匹配→合同→执行→跟踪→对账能够真实贯通；
- 地图来自高德真实底图；
- 公路路径来自正式路线服务；
- GPS/AIS/铁路节点来自正式接口或明确标识的数据来源；
- 业务页面不把测试数据伪装成生产事实；
- AI 不越权、不擅自执行关键业务；
- 核心流程均通过 Playwright 在真实浏览器中完成。

始终以以下原则作为最高标准：

**真实可运行、真实可操作、真实可持久化、真实可授权、真实可追溯、真实地图交互、可持续扩展。**
