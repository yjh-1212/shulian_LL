# Phase 4 供需匹配验收

验收日期：2026-10-01。环境：本地 SQLite、NestJS API、Vue / Element Plus，Edge 可见浏览器与 Codex 内置浏览器。全部业务样例均为开发验收数据。

## 已实现

- `/matches` 单一一级入口，需求大厅 / 供给大厅两个内部页签，默认粮食示意卡片，可切换列表。
- 关键词、状态、公开/定向、需求/完整方案、粮种、运输方式、地区、数量区间、发运/服务日期、指定承运主体筛选；分页、排序、选择导出、详情深链。
- 原运输需求发布接入大厅；已选、有效且关联本企业需求的完整方案发布；有效供给反向对接生成定向业务。
- 整单报价：数量、总价或每吨单价、含税口径、发运/到达时间、能力说明、报价有效期、原方案承接情况及备注。
- 多轮报价、还价、接受、拒绝与撤回；历史条款不可覆盖；贸易方集中比较报价，物流方只见本企业报价。
- 贸易方确认已被双方接受的当前条款，生成承运确认及最终价格。需求可开启数量分配，完整方案整体承接。
- 整数公斤/分计量、乐观版本与事务校验、同一需求最多一个有效发布、同一报价最多一个有效确认，防止重复和超量。
- 取消承运确认保留历史并释放落实数量；关闭、到期、重新匹配；需求页显示匹配进度与落实吨数。
- 发布/议价/确认/取消与到期操作留审计记录，平台可查看、不可参与商务动作。角色授权配置也限制主体类型。
- 升级前的发布记录保留，按迁移时可用资料补齐快照并明确标记；隐藏预算和联系方式不进入外部公开投影。

### 浏览器实际执行

1. 贸易 A 发布 8 吨整单需求，并检查截止时间必填提示。
2. 物流 A 报 3200 元；物流 B 报 3400 元。分别登录验证双方看不到对手身份和价格。
3. 贸易 A 在对比表看到两家报价，对物流 A 还价 3000 元。
4. 物流 A 接受新条款，贸易 A 在数量/金额确认弹窗确认承运。
5. 刷新后仍显示 8 吨、成交 3000 元与完整议价历史；需求页同步匹配完成。
6. 供给卡片选择本企业需求，自动指定供给所属物流 A。物流 B 直接请求详情 API 返回 404，避免暴露定向记录的存在。
7. 查询、导出所选记录、无结果空态、390px 无页面横向溢出。

## 业务边界

- 手工求解未关联订单需求时仍作为方案比选；正式发布要求关联本企业有效需求。完整方案不允许拆区段或按数量拆分报价。
- 匹配大厅采用城市范围检查供给适配，精确地址匹配按用户要求继续暂缓。
- 班列/船期仍是注明来源的参考服务，实际运力和班期由运营商协商确认。
- 当前交付到承运确认及合同输入数据。合同包签署、联运组织和执行任务继续归 Phase5。
